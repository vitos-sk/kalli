# Промт: доработка справочника pentest/cheats

> Скопируй всё ниже в новую сессию Claude Code (из корня проекта). Перед запуском закоммить или отложи текущие правки в рабочем дереве (в `git status` ~19 изменённых файлов), чтобы изменения агента не смешались с ними.

---

## Роль и цель

Ты — продуктовый редактор и разработчик справочника **pentest/cheats** (React + TS + Vite, контент в `src/branches/*.ts`, `src/topics/*.ts`, `src/lib/*`). Справочник для новичка, на русском, простыми словами, проверяет только **своё** (свой компьютер, роутер, проекты, сайт и домен). Приложение ничего не выполняет, только показывает готовые команды и разбирает вставленный вывод.

**Главная цель доработки:** из любого направления человек доходит по справочнику до результата без тупиков, без повторов и без необходимости самому догадываться, куда идти дальше.

**Критерий успеха:** для каждой цели из списка ниже существует ОДИН понятный путь «хочу → шаги → готово, когда… → что дальше», и по нему можно пройти с нуля, не выходя из справочника.

Отвечай и пиши весь контент по-русски, простыми словами (как для новичка), в стиле существующих текстов.

## Порядок работы

1. **Сначала аудит, код не трогай.** Прочитай всё из раздела «Что уже найдено» и перепроверь по коду (находки сделаны быстрым проходом, могли быть неточности). Составь итоговую таблицу дублей и тупиков.
2. **Покажи план и дождись моего «ок».** План: что объединяешь, что удаляешь, что пишешь с нуля, в каком порядке.
3. **Делай маленькими шагами** (по одному блоку из плана), после каждого `npm run build` (проверка типов) и скрипт-проверка ссылок (см. ниже). Не делай больших рефакторингов оболочки, если задачу можно решить в контенте.
4. В конце: прогон по каждой цели из «Карты целей» руками (по ссылкам в интерфейсе, `npm run dev`) и отчёт, где путь проходит, где нет.

### B. Параллельные структуры, которые делают одно и то же

- **Вопросы и ответы** (`topics`), **Что делать, если…** (`situations`) и **Что подставлять** — три формата «проблема → короткий ответ → команда». Человек не знает, куда идти.
- Два дерева тем: `topics` (basics, my-network, my-projects, devices, site-domain, reading-output, practice) и `branches` (home-network, own-site, port-scanning, recon…). Названия и границы не совпадают: `my-network` ≠ `home-network`, `devices` и `my-projects` живут в `topics`, но их «инструмент» находится в ветке `port-scanning`.
- Три «входа для новичка»: **С чего начать**, **Маршрут новичка** (`lib/route.ts` + `RoutePage`), **Вопросы и ответы**. Они пересекаются и друг на друга не ссылаются последовательно.
- Три отдельных вида прогресса: `learned` (ветка изучена), `playbookDone` (шаги сценария), `understood` (вопрос понят) + `favorites` + `notes`. Нигде нет единой картины «что я прошёл».
- «Инструмент» (`SampleTool`) в 4 из 4 готовых веток по сути одинаков (выбери пример → напечатать в терминал), а «Разобрать вывод» — отдельная страница. Новичку непонятно, где вставлять свой вывод.

### C. Тупики и недоделки

- 3 ветки-заглушки «скоро»: `web`, `passwords`, `exploit`. На них ведут `nextSteps` из других веток и этапы маршрута (`route.ts`) — человек доходит до «открыть» и упирается в пустоту. Нужно решение: либо написать, либо убрать из навигации и маршрута, либо честно объяснить «этого в справочнике нет, вот куда идти дальше».
- Нет веток под цели, которые уже задекларированы в `route.ts`/README: проверка Wi-Fi/роутера на слабые пароли, проверка веб-уязвимостей своего проекта, «как исправить найденное» (сейчас «Закрой лишнее» — один абзац в конце сценария без команд и шагов).
- `StartPage` — статичная страница, не связанная с `STAGES`: «первый запуск за минуту» ведёт на `playbooks` и `route`, а не на конкретный сценарий.
- Порядок веток в сайдбаре (`order` 5, 6, 7, 10, 20, 30, 50) не совпадает с логикой «для новичка»: «Сканирование портов» (order 10) стоит после «Разведки», хотя новичку нужно раньше.
- `01-port-scanning.ts` — 589 строк и смесь «nmap-справочника» с «инвентаризацией домашней сети». Ветка перегружена и размыта.
- Ссылки (`link.to`, `related`, `situationId`, `playbooks/…`) проверяются только глазами. Идентификаторы ситуаций глобальные (`sit-${id}`), коллизии между ветками не проверяются.

## Что сделать

### 1. Карта целей (основа всего)

Составь `docs/goals.md`: список **реальных целей пользователя** на языке человека, например:

- узнать свой IP и адрес роутера
- понять, кто подключён к моему Wi-Fi, и убрать чужого
- проверить и закрыть роутер
- понять, какие мои проекты видны всей сети, и спрятать их
- найти и защитить камеры/принтеры/умный дом
- проверить сайт и домен (срок домена, сертификат, https, заголовки, почта)
- узнать, что открыто на сервере сайта
- провести разведку по домену (поддомены, архив, утечки)
- разобраться, что значит вывод команды, которую я запустил
- потренироваться легально

Для каждой цели напиши **один путь**: `старт → шаги (команда → что увидишь → «готово, когда…») → как понять, что всё хорошо / плохо → что делать с плохим (конкретные команды или настройки) → следующая цель`. Если по цели путь не собирается из того, что есть, зафиксируй дыру.

### 2. Единый источник правды (убрать дубли)

Главный принцип: **каждый факт пишется один раз, остальные места на него ссылаются или собираются из него автоматически**.

- Для каждой цели оставь одно «каноническое» место (ветка + сценарий). Остальные упоминания заменить на короткий вход со ссылкой.
- Вопросы из `topics`, которые полностью совпадают с `situations`, — объединить: либо один формат «проблема → ответ → команды» с тегом (тема/ветка), либо вопросы только для «что такое X» (понятийные), а действия — только в ситуациях/сценариях. Рекомендую второй вариант: **Вопросы = «что это такое»**, **Ситуации = «что делать»**, **Сценарии = «пошагово, от начала до конца»**.
- Команда определяется один раз (библиотека команд `src/lib/commands` или одна ветка-владелец), а ветки/ситуации/сценарии ссылаются по id. Убрать повторяющиеся `note` / `flags` (flags брать из `glossary`, свои — только для особенного).
- Сценарии `inventory`, `own-router`, `my-network-audit`: свести к одному канону «домашняя сеть» (ветка `home-network`), в `port-scanning` оставить только то, что касается самого nmap.
- Блок «как узнать свой IP / адрес роутера» — оставить в одном месте (`start` или вопрос `my-ip`), везде ссылка.
- Блоки «что можно, что нельзя» — один компонент-предупреждение и один текст.
- Три «входа» (Start / Route / Questions) свести к одному понятному: «С чего начать» с выбором цели («Что хочешь сделать?») → ведёт в путь из `docs/goals.md`.

Если нужен технический механизм (например, `commands.ts` с реестром команд и `getCommand(id)`, либо `Situation.relatedQuestions`), предложи минимальный вариант в плане, не делай «большой фреймворк».

### 3. Тупики

- Для `web`, `passwords`, `exploit` реши вместе со мной (в плане): написать минимально рабочие ветки по теме «своё» **или** убрать из маршрута и `nextSteps`. Нельзя оставлять ссылку, которая ведёт в пустоту.
- Для каждой готовой ветки: в конце гайда и каждого сценария — блок «что дальше», ведущий только в существующие страницы. Каждый сценарий заканчивается «готово, когда…» и ссылкой на следующий.
- «Закрой лишнее» раскрыть в отдельные ситуации/шаги: что именно сделать (Mac/Linux/Windows, роутер: куда зайти, какую настройку выключить), как проверить повторно.

### 4. Навигация и структура

- Один список направлений в сайдбаре, упорядоченный по пути новичка (дом → сайт → разведка → порты → …), без «заглушек».
- Поиск (`lib/search.ts`) должен выдавать **один** результат на тему, а не пять копий (вопрос + ситуация + команда + гайд + сценарий). Либо группировать результаты по цели, либо подавлять дубли.
- Единый прогресс: одна страница «Мой прогресс» (цели → сценарии → шаги), без трёх разных механик. Убрать лишнее хранилище в `lib/store.ts`.
- «Разобрать вывод» доступен прямо на странице ветки/сценария (кнопка или встроенное поле), а не только отдельной страницей.

### 5. Проверки качества (автоматические)

Добавь скрипт `scripts/check-content.ts` (запуск `npm run check:content`), который падает, если:

- `link.to`, `related`, `situationId`, `nextSteps.branchId`, `Playbook.steps[].sampleId`, `Situation.cmds` указывают на несуществующее;
- id ситуаций/сценариев/вопросов повторяются;
- ровно одна и та же команда имеет несколько разных `note`;
- в `nextSteps` или маршруте есть ветка с `soon: true`;
- у сценария нет «готово, когда…» хотя бы в одном шаге;
- в `Situation.cmds` указана команда, которой нет в `commands` ветки (сейчас такой проверки нет, и карточка молча не отрисуется — см. `Situations.tsx`).

## Ограничения

- Только русский, простые слова, без канцелярита. Стиль и тон соседних текстов не менять.
- Ничего не выполняй и не сканируй, не добавляй сетевых запросов к чужому.
- Ничего чужого не сканировать: во всех примерах только свои цели, `example.com`, `scanme.nmap.org`.
- Оболочку (`App.tsx`, `Sidebar`, `BranchPage`) менять только там, где без этого не решить дубль или тупик.
- Не коммить без моей команды. После каждого блока — краткий отчёт: что изменено, что удалено, какие проверки прошли.
- Перед удалением любого контента покажи, на что он ссылался и чем заменён.

## Формат ответа на первом шаге

1. Таблица дублей (что, где, предложение «оставить тут / заменить ссылкой»).
2. Таблица тупиков и дыр по целям.
3. Предлагаемая структура навигации (дерево).
4. План работ по шагам с оценкой объёма и рисков.
5. Вопросы ко мне — только если без ответа нельзя выбрать вариант (например, писать ли `web`/`passwords`/`exploit`).
